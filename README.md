# FitBook

Учебная информационная система для записи на спортивные занятия. Приложение работает с PostgreSQL в Supabase, использует Supabase Auth, две роли, недельное расписание, бизнес-правила, историю статусов и административную аналитику.

## Роли

### Пользователь
- регистрация и вход через Supabase Auth;
- недельное расписание Пн-Вс;
- фильтры по направлению, тренеру и уровню;
- просмотр свободных мест;
- запись на занятие;
- раздел «Мои записи»;
- карточка записи и история изменения статусов;
- отмена записи более чем за 2 часа до занятия.

### Администратор
- отдельная административная панель;
- 4 основных KPI и дополнительные показатели;
- график «Записи по направлениям»;
- график «Состояние записей»;
- фильтр аналитики: 7 дней, 30 дней, всё время;
- добавление и отмена занятий;
- просмотр участников;
- просмотр всех клиентских записей;
- отметка «Посещено» и административная отмена записи.

## Новые функции лабораторной

В проекте реализовано больше трёх новых функций:

1. **История изменения статусов**. Каждое создание записи и изменение её статуса сохраняется в отдельной таблице `booking_status_history`.
2. **Расписание**. Занятия отображаются по неделям Пн-Вс, можно переходить на предыдущую и следующую неделю.
3. **Фильтрация по нескольким параметрам**. Расписание фильтруется по направлению, тренеру и уровню.
4. **Ограничение количества мест**. Нельзя записаться, если `booked_count >= capacity`.
5. **Контроль занятости временных интервалов**. Нельзя иметь две подтверждённые записи на пересекающееся время.

Минимум одна новая функция использует дополнительную таблицу: история статусов хранится в `booking_status_history`.

## Обязательное бизнес-правило

Критичные ограничения проверяются не только интерфейсом, но и PostgreSQL RPC-функцией `book_session`:
- нельзя записаться сверх вместимости;
- нельзя повторно записаться на то же активное занятие;
- нельзя создать пересекающиеся подтверждённые записи;
- нельзя записаться на прошедшее или отменённое занятие.

## База данных

Рабочие таблицы `public`:
- `profiles`;
- `trainers`;
- `sessions`;
- `bookings`;
- `booking_status_history`.

Системная таблица `auth.users` отвечает за учётные записи пользователей.

Основные связи:
- `auth.users 1 -> 1 profiles`;
- `trainers 1 -> N sessions`;
- `profiles 1 -> N bookings`;
- `sessions 1 -> N bookings`;
- `bookings 1 -> N booking_status_history`.

## Архитектура

```text
Браузер
  -> Express /api/config
  -> Supabase JS
  -> Supabase Auth + PostgreSQL
       -> RLS
       -> RPC book_session / cancel_booking / mark_booking_visited / cancel_session
```

Express отдаёт клиенту только `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY`. Начальная учётная запись администратора задаётся в серверном `.env`. Если `SUPABASE_SERVICE_ROLE_KEY` доступен, сервер использует официальный Admin API. В учебной сборке без service role используется защищённый одноразовый bootstrap RPC: пароль администратора остаётся только на сервере, а в базе хранится только SHA-256 bootstrap-секрета.

## Локальный запуск

1. Установить Node.js 20+.
2. Выполнить `npm install`.
3. Создать `.env` по примеру `.env.example`.
4. Для текущей локальной сборки `.env` уже содержит URL и publishable key проекта `fitbook-final`.
5. Выполнить `npm start`.
6. Открыть `http://localhost:3000`.

На учебных компьютерах PowerShell может блокировать `npm.ps1`. В таком случае используйте:

```powershell
npm.cmd install
npm.cmd start
```

## Переменные окружения

```env
PORT=3000
SUPABASE_URL=
SUPABASE_PUBLISHABLE_KEY=
SUPABASE_SERVICE_ROLE_KEY=
ADMIN_EMAIL=
ADMIN_PASSWORD=
ADMIN_BOOTSTRAP_SECRET=
DEMO_USER_EMAIL=
DEMO_USER_PASSWORD=
DEMO_SEED=false
```

`.env` находится в `.gitignore`. В GitHub публикуется только `.env.example` без реальных значений.

В готовой локальной сборке заполнены `ADMIN_EMAIL`, `ADMIN_PASSWORD` и `ADMIN_BOOTSTRAP_SECRET`, поэтому при первом запуске сервер автоматически создаёт начального администратора и назначает роль `admin`. `SUPABASE_SERVICE_ROLE_KEY` оставлен пустым и для этой учебной сборки не требуется. Если он будет указан позже, сервер переключится на официальный Supabase Admin API. Ни пароль администратора, ни bootstrap-секрет, ни service role key не передаются в `/api/config` или клиентский JavaScript.

## SQL

- `supabase/schema.sql` - таблицы, ограничения, RLS, триггеры и RPC;
- `supabase/seed.sql` - 4 тренера и 17 занятий текущей/следующей недели;
- `supabase/checks.sql` - WHERE, ORDER BY, JOIN, COUNT, GROUP BY и аналитический запрос;
- `supabase/bootstrap.sql` - защищённая серверная инициализация первой учётной записи администратора;
- `supabase/promote_admin.sql` - запасной учебный способ назначения роли уже зарегистрированному аккаунту.

## Безопасность

- RLS включён на всех 5 прикладных таблицах;
- пользователь видит только свои записи;
- административные операции повторно проверяют роль в PostgreSQL;
- изменение статусов выполняется RPC-функциями;
- пользователь не может назначить себе `admin` через форму;
- пароли хранятся в Supabase Auth, а не в `profiles`;
- вывод технических ошибок пользователю заменяется понятными сообщениями;
- текстовые значения экранируются перед вставкой в HTML.

## Демонстрационные учётные записи

В текущем Supabase-проекте `fitbook-final` уже подготовлены подтверждённые демонстрационные учётные записи:

- администратор: `admin.fitbook@example.com` / `<задаётся через переменные окружения>`;
- демо-пользователь: `demo.fitbook@example.com` / `<задаётся через переменные окружения>`.

Для демо-пользователя в базе уже создано 6 записей с разными статусами, поэтому обе диаграммы административной панели сразу показывают данные. Серверный bootstrap остаётся идемпотентным: при запуске он проверяет существование администратора и не создаёт дубль. Реальные пароли и bootstrap-секрет находятся только в локальном `.env`/переменных окружения хостинга и не должны публиковаться в GitHub.

## Развёртывание

Для публикации выбран **Render**, потому что он поддерживает Node.js/Express и позволяет хранить секретные переменные окружения вне GitHub. Репозиторий содержит `render.yaml` с build/start-командами и публичной конфигурацией Supabase. Пароли и bootstrap-секрет задаются в Render как Secret Environment Variables.

Build command:

```text
npm install
```

Start command:

```text
npm start
```

После развёртывания публичный URL добавляется в этот раздел и проверяется по `docs/DEMO-CHECKLIST.md`.
